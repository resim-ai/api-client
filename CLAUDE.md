## What this is

The ReSim CLI (the `signalflag` binary): a Go command-line tool for the ReSim API. Most of `api/` and `bff/` is **generated code** — the REST client is generated from the rerun OpenAPI spec via `oapi-codegen`, and the BFF GraphQL client via `genqlient`. Module: `github.com/resim-ai/api-client` (Go 1.23).

## Commands

- Build:   `go build -o signalflag ./cmd/signalflag`   (CI builds all: `go build ./...`)
- Test:    `go test ./... -race`             # single test: `go test -v -run TestName ./path/to/pkg`
- E2E:     `go test -v -tags end_to_end -count 1 ./testing`   # needs SIGNALFLAG_CLIENT_ID / SIGNALFLAG_CLIENT_SECRET + CONFIG (staging|prod)
- Lint:    `go fmt ./...` and `go vet ./...`  # run BEFORE pushing — CI fails if either emits any output
- Codegen: `go generate ./...`               # regen after OpenAPI / GraphQL schema changes; generated files are committed

There is no Justfile or Makefile — drive everything with the `go` toolchain directly. `staticcheck.conf` configures staticcheck (whitelists the dot-import of `ptr`) if you choose to run it; it is not part of the CI gate.

## PRs

Uses **gh** — `git push -u origin <branch>` then `gh pr create`; a large change goes up as a GitHub stacked-PR chain (`gh stack`).

## Testing conventions

- Standard Go `testing` package; `*_test.go` files sit next to the code they cover (e.g. `cmd/signalflag/commands/*_test.go`).
- CI runs the full suite with `-race`.
- The end-to-end suite in `testing/` is gated behind the `end_to_end` build tag, so it is skipped by a plain `go test ./...`. It hits a live deployment and needs client credentials plus `CONFIG` (and `DEPLOYMENT` for a customer dev deployment). Fixtures live in `testing/data/`.
- API-client mocks are generated by mockery into `api/mocks/` (config: `api/.mockery.yaml`) — do not hand-write them.

## Gotchas

- **Generated code is committed and large — never hand-edit it.** `api/client.gen.go` (~1 MB), `bff/queries.gen.go`, and `api/mocks/` are all outputs of `go generate ./...`. Change the source (OpenAPI spec / `bff/queries/` GraphQL / mockery config) and regenerate instead.
- **`go generate` fetches the spec over the network.** `api/generate.go` pulls the OpenAPI spec from `https://api.resim.ai/v1/openapi.yaml` (production URL) — regen needs internet access, and the client tracks whatever the prod spec currently is.
- The `ptr` package is intentionally dot-imported; staticcheck is configured to allow it. Keep new dot-imports out.
- The built `signalflag` binary and `.env.local` are gitignored — don't commit them.

## Directory map

- `cmd/signalflag/`         — CLI entrypoint (`main`); `cmd/signalflag/commands/` holds the cobra commands (agents, batch, build, experience, metrics, project, sweep, test_suites, …) with adjacent `_test.go` files.
- `api/`               — generated REST client (`client.gen.go`), `generate.go` (oapi-codegen + mockery directives), `client.cfg.yml`, `.mockery.yaml`, and `mocks/`.
- `bff/`               — GraphQL BFF client: `queries/` (source `.graphql`), `queries.gen.go` (genqlient output), `genqlient.yaml`, `cmd/` (the generator).
- `auth/`              — authentication (token caching, client-credentials / username-password flows, static API keys).
- `ptr/`               — pointer helper utilities (dot-imported).
- `testing/`           — end-to-end test (`end_to_end` tag) and `data/` fixtures.
- `docs/plans/`        — per-repo plan documents.
- `.github/workflows/` — CI: lint-and-build, build-image, release-cli.
- `.devcontainer/`     — dev container config.

## Writing conventions

Shared across ReSim repos. Full policies: `resim-orient` → Code Comments, Never Post Comments Unsolicited; `/comment-audit` sweeps a branch.

### Length

Most agent-written text goes unread because it is too long or dense to skim. This applies to every comment, README, doc, plan, PR description and memory note.

- Lead with the point. Keep sentences short and paragraphs to one to three sentences.
- Say each thing once. Link to the code, `--help` or another doc instead of restating it.
- Leave out chronology, everything you checked, caveats for unlikely cases and edge-case trivia.
- Budgets: a comment ≤ 3 lines, a README section ≤ 15 lines, a whole README ≤ 80 lines, a memory note ≤ 10 lines. If you run over, cut or move detail one level down rather than packing it in.
- Before finishing, delete every sentence a reader would not miss.

### Code comments

Keep useful existing comments: run instructions, test purpose, maintenance rules for templates or generated code, external contracts, non-obvious constraints. Remove a comment only when it is stale, misleading, redundant or narrates an edit. New comments state the constraint, not how you found it.

Never reference ephemeral context; it belongs in the PR description:

- Plans or sub-task labels (`see plan U5`, `KTD`), Linear IDs (`WOB-4129`), other PRs in a stack, or follow-up work.
- Measurements, timings and investigation narration.
- Change history: `now uses X`, `no longer Y`, `per the design`, `added for the Y flow`.

Don't restate well-named code (`// returns the user` above `GetUser()`).

### PR descriptions

Write for engineers and product owners who missed the conversation, in about **150–250 words** for a substantive change and less for a simple one. In order, without mandatory headings:

1. What changes and why, in one or two sentences.
2. Two to four key pieces, if there are distinct ones.
3. Why it matters to the customer or engineering workflow.
4. Dependencies, rollout prerequisites and verification, when relevant.

Omit file inventories, walkthroughs, commands, logs, chronology, abandoned approaches and stack bookkeeping. Link another PR only for a real dependency. Ground claims in the final diff. The `pr-describer` agent's example sets the depth and tone.

### Changelog entries

One or two lines for someone deciding whether a version matters to them: what changed, the parent PR, and any behaviour they need to know.
